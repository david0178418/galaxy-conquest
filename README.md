# Galaxy Conquest

A touch-first, single-player real-time strategy game. Expand between planets, choose troops, ships, or defense platforms, and conquer the rival. Battles take place within a single star system.

Bun serves and bundles HTML/TypeScript/CSS directly. ECSpresso 0.24.1 runs the tactical simulation; PixiJS 8.19.0 renders units beneath DOM planets and controls.

The [current game design](docs/game-design.md) documents star system combat, production, victory, persistence, and remaining playtest questions. Technical evidence is in [performance diagnostics](docs/performance-diagnostics.md), [renderer migration](docs/renderer-migration.md), and [viewport culling](docs/viewport-culling.md).

```sh
bun install --frozen-lockfile
bun run dev
```

Open http://localhost:3000. `bun run check` runs lint, simulation tests, strict TypeScript checks, and a production build into `dist/`.

GitHub Pages publishes the production build at https://david0178418.github.io/galaxy-conquest/. The [deployment workflow](.github/workflows/deploy.yml) runs checks, builds, and deploys on pushes to `master`; it can also be run manually from the Actions tab on `master`. Repository Settings → Pages must use **GitHub Actions** as the build source. Bundled asset URLs are relative, so the same build works under `/galaxy-conquest/` and at a domain root.

The production build is an installable PWA. Open the standalone HTTPS site and use your browser's **Install app** command; on iPhone/iPad, use Safari's **Share → Add to Home Screen**. It opens in its own window using the existing GC icon. Installation availability depends on the browser; embedded player cards should be opened as the standalone site first.

After the first online visit finishes caching, the game can reopen and play offline, including local profiles and saves. New releases download in the background and activate after all game windows/tabs close; an ongoing conquest is never reloaded automatically. Saves remain in IndexedDB and retain the browser/site storage limits described below. Workbox generates the offline cache from build assets; source maps and the social poster are excluded. PWA registration is production-only, so `bun run dev` does not install a worker. Serve `dist/` over localhost or HTTPS to test installation/offline behavior.

The page includes X player-card metadata intended to embed the game in a post, using [assets/x-card.jpg](assets/x-card.jpg) as the poster. Metadata and a successful build alone do not verify live inline playback on X. Use the deployed standalone URL, including the trailing slash, when checking card behavior. An embedding host must permit framing.

## Skirmish and local profiles

The title screen offers up to 10 local profiles. On first use, a **Player** profile is created and selected automatically so you can start immediately. You can rename it or create another profile. Each profile has one ongoing star system battle: **Continue** restores its saved map and game state paused, and **New game** starts over after confirmation. Rename keeps progress; deleting a profile requires confirmation and removes only that profile. Choose **Save** at any time or rely on periodic autosaves, including while paused. Save status and failures appear in the game header and game menu.

Starting a new conquest or replacing the current map requires confirmation when it would replace progress. From **New game**, choose **Small** (12 worlds), **Medium** (18), or **Large** (30), inspect the preview, and use **Generate another map** to reroll it. **Start conquest** launches that exact layout with one world and three ships per side. The optional **Start with carriers** skirmish setting is off by default; enabling it adds one carrier per side with 20 crew and three docked ships. The current carrier production rate is provisionally set to 25% of the standard home-world rate; it remains unvalidated for balance. This is a standalone star-system feature; there is no campaign layer. Existing saves without carriers remain compatible. Generated worlds have mirrored positions and resources for equal expansion opportunities, with at least 216 units between centers. **Restart map** replays the same layout.

Profiles and conquests use IndexedDB in the current browser and site. They do not sync between devices, browsers, hosting origins, or embedded and standalone versions. Clearing site data or browser storage eviction can remove them. Embedded browsers may block or partition storage; open the standalone game if saves are unavailable. There is no account, cloud backup, or export/import.

Save validation has format safety bounds independent of gameplay tuning: at most 100,000 troops per planet or cargo units per transport; production-rate values up to 10,000 and production progress below 10,000; map dimensions up to 10,000; unit positions within ±20,000; and planet radii up to 1,000. A save outside those bounds cannot be continued; validation leaves the stored profile data unchanged.

The star map fills the viewport. Drag to pan; scroll up to zoom in and down to zoom out around the pointer, or pinch to zoom on touchscreens. Horizontal scrolling pans sideways. Use Fullscreen on the title screen or in the game menu to enter or leave fullscreen where supported. Focus the map and use arrow keys to pan with a keyboard. Selecting a planet or carrier opens a fixed command panel on the right (bottom on phones); rival and neutral holdings show their information. The game menu contains fullscreen, restart, new game, profiles, scenarios, pace, save status, and help. The compact top bar keeps planet counts, time, Orders, Save, Pause, and the menu in view. Widths of 699px and below hide the title and the header save-status line; widths of 359px and below also hide the clock. The Save button and the menu's save status stay available. Production controls appear only when you select a holding you own.

Tap or left-click a blue planet or carrier to select it. On touch, hold an entity for 500 ms to dispatch 50% of the selected sources’ troops and ships; with a mouse, right-click the entity. A short tap or left click only changes selection. With one of your carriers selected, click empty map space to set its movement destination. Dispatch to a planet or carrier uses the same hold or right-click gestures as other entities. The carrier’s **Launch docked ships** action sends its selected share into local space, including during blockade. Dragging, pinching, or cancelling a touch cancels a pending hold. Change the send amount or choose ships/troops only in the command panel. Production buttons change the selected entities; defense platforms never travel. Multi-select gathers several sources; finish selection before holding or right-clicking a destination. Tap a selected source again or use Clear selection to deselect. Tap your blue orbital presence over an enemy world to redirect blockading ships.

Troops capture surfaces; ships and defense platforms fight in orbit. Troops launch in free, disposable transports carrying up to 10 each. Ships travel at 23.75 world units per simulation second; transports travel at half that speed (11.875), so escorts can arrive first. Carriers travel at 5.9375 units per second: 25% of ship speed and half transport speed. Ships and transports sent to a moving carrier update their intercept as it moves. Ships can intercept hostile travelers within 48 units; transports take fire and keep moving. Landings wait for hostile orbital resistance to clear. A dashed hostile ring means blockade, preventing departures from ordinary planets while production continues. A carrier can keep moving and launch its docked ships during blockade, but docking waits until hostile resistance clears. These permissions do not change ordinary planet departure restrictions. Carriers cannot be damaged or destroyed, have no platforms or independent weapons, and have no crew or docked-ship capacity limits. Boarding transfers the carrier and all docked ships and stops its movement; ships already launched remain independent. An owned carrier counts as a surviving holding for victory. Orbital control alone never captures a planet or carrier. See [tactical rules and tuning](docs/game-design.md#tactical-rules) for targeting, arrival grace, capture, and production details.

The **Prototype lab** contains a normal AI skirmish, an established blockade, and a defended invasion. The skirmish starts with the rival AI on. The blockade and invasion labs start with AI off; enable it on those labs when useful. In carrier skirmishes, the AI uses carriers for production and dispatch and launches docked ships locally to contest blockaders; it has no strategic carrier movement strategy, so its carriers stay stationary. Restart resets the scenario; pace changes persist. Pause freezes movement, production, combat, and AI while keeping map navigation, selection, orders, and production changes available. Orders allocate units immediately, so repeated sends use the remaining stock; movement and production progress continue on resume, without catching up paused time. Open **Orders** beside Pause to view active dispatches. The drawer shares the command panel’s space and filters incoming, outgoing, and returning routes to the selected planet (or selected sources). **Show all** keeps the planet selection while showing every route; changing the selection restores automatic filtering. Select an order row to highlight its route without changing the selected planet. **Cancel launch** releases a paused dispatch’s reserved ships and troops before departure. **Recall** turns surviving escorts and loaded transports around at their current positions and sends each back to its own departure world; recalling during pause sets the course but movement waits for resume. Returning orders remain visible until arrival. Waiting transports and their escorts can be recalled before landing; completed arrivals leave the drawer. If a departure world changes hands, normal arrival/combat rules apply there. Switching tabs pauses tactical simulation automatically; it resumes on return if it was running before the tab was hidden. Win by taking every rival planet or carrier.

The [design reference](docs/game-design.md) includes map sizes, starting forces, AI behavior, tuning values, implementation entrypoints, and acceptance limits. There is no networking, controller support, audio, cloud sync, or arbitrary mid-flight retargeting. Physical-device touch comfort, combat readability, balance, and match feel require playtesting.
